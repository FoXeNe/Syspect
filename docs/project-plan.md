# Syspect - план проекта

На своём VPS мне приходилось вручную проверять, куда делось место: в Docker-образы, кэш сборки или журналы. Хочу, чтобы `syspect analyze` показывал это в одном отчёте. Тот же отчёт должен помочь, если сервер тормозит, но неясно, упирается он в CPU, память или диск. Размер сервера для Syspect не важен.

Пишу на Go, чтобы выпустить один Linux-бинарник. Заодно хочу разобраться с `/proc`, cgroups v2, Docker Engine API и systemd journal.

## Пример отчёта

Цифры для примера, не результат замера:

```text
MEMORY
  RAM:          1 GiB
  Available:    183 MiB
  Swap used:    680 MiB / 2 GiB
  PSI some:     avg10=8.20

CPU / I/O
  CPU busy:     83% over 1s
  I/O PSI some: avg10=0.00

DISK
  Root free:    850 MiB / 10 GiB
  Docker images: 2.4 GiB
  Build cache:   1.1 GiB
  Journal:       740 MiB

WHAT TO CHECK
  Memory stalls: check which processes use the most RAM and look for OOM events.
  Low disk space: check how much Docker build cache is marked reclaimable.
```

## Что собрать

- Память: `MemTotal`, `MemAvailable`, swap и `/proc/pressure/memory`. Если есть доступ, показать события OOM и лимиты памяти контейнеров.
- CPU: загрузку за интервал по `/proc/stat`, а также процессы, которые за этот интервал использовали больше всего CPU. Отдельно показать процессы с наибольшим RSS и пояснить, что RSS включает общие страницы.
- I/O: `/proc/pressure/io`, позже добавить счётчики из `/proc/diskstats`. Если нужен темп чтения или записи, взять разницу между двумя замерами.
- Диск: сначала размер и доступное место на `/`, затем другие файловые системы и крупные каталоги. Отмечать каталоги, которые не удалось прочитать.
- Docker: контейнеры, образы и кэш сборки. Показывать общий размер и оценку освобождаемого места отдельно.
- Журналы: размер journal, настройки хранения и доступные записи о сбоях.

Если Docker не запущен, PSI не поддерживается или не хватает прав, написать об этом в отчёте. Отсутствие данных не означает ноль.

## Что говорить в отчёте

Писать, что измерили, что это может означать и как проверить. Например, ненулевой swap не означает, что памяти не хватает прямо сейчас. Если PSI показывает задержки из-за памяти, стоит посмотреть, какие процессы её используют, и проверить записи об OOM. Не считать файловый кэш проблемой сам по себе. Load average не выдавать за процент загрузки CPU, а один замер не называть всплеском.

Если у контейнера нет лимита памяти, сообщить об этом без совета поставить случайное число. Если журнал вырос, предложить проверить его настройки хранения. Не считать весь размер журнала, образов или кэша доступным к удалению. Оценку освобождаемого места приводить только там, где источник даёт данные о том, что можно удалить.

## MVP на 10-14 дней

1. **Базовый отчёт (2-3 дня).** Создать Go-модуль и `syspect analyze`. Вывести RAM, swap, место на `/`, загрузку CPU и PSI. Добавить тесты парсинга `/proc/meminfo` на фикстурах.
2. **Процессы, Docker и журналы (3-4 дня).** Добавить список процессов по CPU и RSS, статистику Docker и размер systemd journal. Проверить, что отчёт работает без Docker и systemd, а также при ограниченном доступе к сокету и журналам.
3. **Подсказки и JSON (3-4 дня).** Добавить диагностические подсказки, `--json` и сборку с тестами в GitHub Actions. Проверить отчёт под нагрузкой в VM или на тестовом VPS.
4. **Документация и релиз (1-3 дня).** Добавить инструкцию по установке и пример вывода. Описать два случая: заполненный тестовый диск или Docker-кэш и контейнер с ограниченной RAM. Опубликовать Linux-бинарник.

MVP готов, когда бинарник работает на поддерживаемом Linux без Go, анализ ничего не меняет в системе, а недоступность одного источника не мешает показать остальные данные. В README должны быть установка, пример отчёта и ограничения; в репозитории должны быть тесты и релиз.

## После MVP

- Добавить `syspect snapshot` и `syspect diff` для сравнения двух отчётов.
- Разобраться подробнее с OOM и cgroups v2. Добавить тесты под нагрузкой на CPU, память и диск.
- Научиться находить растущие логи и подсказывать, где проверить настройки logrotate и journald.
- Если понадобится очистка, начать с `syspect cleanup --dry-run`. Для реального удаления сначала показать объекты, ожидаемый эффект и последствия, затем попросить подтверждение. Не трогать активные контейнеры и произвольные файлы, не удалять volumes и данные БД по умолчанию и не запускать `docker system prune -a --volumes`. Если Docker пометил объект как reclaimable, это не значит, что он не нужен приложению.

Веб-панель, фоновый мониторинг, Kubernetes, сбор метрик с нескольких серверов и сброс page cache не планируются для MVP.

## Что показать в README

Начать с проблемы, которая действительно возникала на моём сервере: кончалось место или не хватало памяти. Сохранить отчёт до вмешательства, записать, как проверил предположение, что исправил вручную и как изменились показания после этого.
